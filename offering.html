Cadence, specifically

The evidence on this site runs on SIMetrix/SIMPLIS, Python and SystemVerilog, because those are the tools I license or that need no licence. A Cadence shop will want to know what happens to SKILL, OCEAN, Spectre and ADE.

I have automated Cadence flows before, writing SKILL and the OCEAN scripts that drive the simulator, under agreements that keep that work with the client. None of it appears on this site, and that is the rule I would apply to yours.

What does appear is the method, and it is the same whatever the tool. A generator writes the script. A checker validates it without running the tool: every function against a whitelist built from the documentation installed on your machines, every call's argument count against real usage in your own scripts, and a script that fails the check never reaches your simulator. That does not make generated code correct. It makes it not hallucinated, which is the failure that bites. In week two it is built and proven against your installed release and your PDK, on your licence.

Why the local box, specifically

Three reasons, and they all point the same way.

The API surface is release-specific. A generator's whitelist has to come from the documentation installed on your machines, not from a model's recollection of a different version. That is why retrieval has to run where your docs live.

The data cannot leave. PDK-adjacent work is foundry-covered. That is a legal fact, not a preference, and your legal team decides where the line sits.

Architecture exploration is where the time goes. A yield-versus-trim-depth sweep is nine simulation campaigns, and each campaign in a real flow is a generated testbench. Making generation cheap and checkable is what turns a week of setup into an afternoon, and that only works next to the tools.

None of it requires a frontier model on your side. It requires a modest local model, grounded by retrieval over documentation already on your disk.

The recipe library

IN DEVELOPMENT

The recipe library is planned and not yet shipping. The first recipes are being built now. Nothing here is available on day one of an engagement, and support pricing does not assume it is. It is described here because it is where the support tiers are going, and you should know what you are buying into.

Each recipe is a short worked example of one automation task, structured so you can adapt it. The first is placing and auto-routing a matched capacitor array: a converter array in the worked example, but the same problem as an R-2R ladder, a current-steering unit-cell array, a thermometer array, or a resistor string. One recipe covers a family, which is the point.

Every recipe has the same five parts, in the same order.

  1. The check, before the prompt. What deterministically proves the output is right. For a matched array: symmetry about both axes, centroid coincidence, unit count matching the intended weights, DRC clean. The check is written first, deliberately. If you cannot state how you would know the result is wrong, the task is not ready to automate.
  2. The prompt skeleton, with the parts that change marked as parameters.
  3. A worked run, start to finish, including exactly what the tool returned.
  4. Adaptation notes. What changes for a different array type, a different bit count, a different matching scheme. This is the part that makes a recipe reusable.
  5. Known failure modes. How it breaks, what the breakage looks like, and which check catches it. Usually the most useful section.

Recipes are recorded on open PDKs and generic structures, never on a client's array, never with client naming or dimensions. The pattern travels between clients; the design never does. That constraint is why the library can be shared at all.

No release cadence is promised. A recipe takes a day or so to build properly, and a promised release rate produces filler. You get the library as it exists and as it grows.
